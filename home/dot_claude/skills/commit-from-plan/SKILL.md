# plan をコミットメッセージに残してコミットする

plan ファイルは git 管理外（`ai-out/`）にあり、この手順の最後で消える。
つまり **plan 本文をコミットメッセージに移すことが、設計の理由を残す唯一の機会**。
差分が語るのは *何を* だけで、*なぜ* と *見送った案* は plan にしかない。

要約しない。切り詰めない。本文をそのまま入れる。

## 手順

### 1. 対象の plan を特定する

```bash
ls ai-out/plans/
```

- 1 本だけならそれを使う。
- 複数あるならユーザーに聞く。今回の作業と無関係な plan を巻き込むと、
  コミットメッセージが嘘になる。
- 1 本も無いなら、このスキルの前提が成立していない。止めて、通常のコミットでよいか確認する。

### 2. コミットする差分を確認する

```bash
git status
git diff --stat
```

何をコミットしようとしているかをユーザーに見せてから `git add` する。
plan と無関係な変更が混ざっていたら、含めてよいか確認する。

### 3. plan からの逸脱を追記する

実装中やレビューで plan と違う形になった点があれば、**plan ファイルの末尾**に追記してから
メッセージを組む:

```markdown

## 実装時の変更
- <plan と違う形にした点と、その理由>
- <レビュー指摘を受けて変えた点>
```

これを書き落とすと、コミットメッセージが実際のコードと食い違う文書として残る。
将来それを信じた人が間違える。逸脱が無いなら追記しない。

### 4. メッセージを組み立てる

```bash
MSG=$(mktemp)
{
  echo "feat(scope): <plan のタイトルを一行にしたもの>"
  echo
  cat ai-out/plans/<slug>.md
} > "$MSG"
```

- subject は Conventional Commits（`feat` / `fix` / `refactor` / `chore` / `docs` / `test`）。
  plan のタイトルをそのまま使えることが多い。`Issue #15: …` のような接頭辞は subject では落とし、
  必要なら subject 末尾に `(#15)` を付ける。
- body は plan 本文まるごと。plan の `# タイトル` 行が残っても構わない。

`-F` でファイルを渡すだけなら `#` 見出しはコメント扱いされず、そのまま残る。
ただし **`-e`（エディタを開く）や `--cleanup=strip` を付けると `#` で始まる行が全部消える**。
plan の見出しが丸ごと落ちるので、この 2 つは使わない。

### 5. 機密が混ざっていないか見る

`$MSG` を一度読む。API キー、トークン、パスワード、個人情報が plan に紛れていないか。
plan ファイルは消えるが、コミットは残る。見つけたら plan 側から削ってから組み直す。

### 6. コミットして plan を消す

```bash
git commit -F "$MSG"
rm ai-out/plans/<slug>.md
```

削除は**コミット成功後**。コミットが失敗したら plan は残す
（消してから失敗すると、設計の記録が完全に消える）。

### 7. 報告する

コミットハッシュと subject、削除した plan のパスをユーザーに伝えて終了。
push はしない（頼まれていなければ）。

## 補足

**1 plan = 1 commit** が既定。分けたいなら plan の側を先に分ける。
1 つの plan を複数コミットに割ると、どのコミットに本文を入れるか決められず、
結局どこかに設計の理由が無いコミットができる。

**`contextual-commits` とは併用しない。** subject の Conventional Commits は共通だが、
body は plan がそのまま入るので `intent:` / `decision:` / `rejected:` といった action line は
書かない。plan の「Context」「対応方針」が既に同じ情報を持っており、二重になる。
plan が無いコミットは `contextual-commits`、plan があるコミットはこのスキル、という住み分け。
