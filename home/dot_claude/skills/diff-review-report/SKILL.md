# 差分レビューレポート

大きな差分は、ファイル順に上から報告しても読めない。読み手が知りたいのは
「**何を意図した変更が幾つあって、そのうちどれが危ないか**」で、
それは diff からは直接読み取れない情報だから、こちらで再構成する必要がある。

このスキルが出すのは、ブラウザで開く 1 枚の HTML。
グループ一覧 → 詳細（意図 + 解説付き diff + 承認チェック）→ 指摘一覧 →
コメント → フィードバック markdown 生成、という導線が入っている。

## 作業ディレクトリ

中間ファイルとレポートはスクラッチパッド（system prompt に記載のセッション用一時ディレクトリ。
無ければ `mktemp -d`）に置く。作業リポジトリを汚さないため。

```bash
W=<scratchpad>/diff-review && mkdir -p "$W"
```

以降 `$SKILL` はこのスキルのディレクトリを指す。

## 手順

### 1. 差分の範囲を決めて hunk を収集する

ユーザーが範囲を言っていなければ、`git status` を見て推測し、
「未コミット全部（`HEAD`）でよいか」を一言確認する。範囲を取り違えると全部やり直しになる。

```bash
python "$SKILL/scripts/collect_diff.py" -o "$W/hunks.json" -- HEAD
```

`--` の後ろは `git diff` にそのまま渡る（`--cached` / `main...HEAD` / `HEAD~3` など）。
stdout に `h001 <file> +3 -1 @@…` という索引が出る。**これがグループ分けの材料**なので、
diff 本文を自分で読み直す前に、まずこの索引でファイルの地図を作る。

未追跡ファイルがあると警告が出る。新規ファイルはレビューで一番見るべき対象なので、
`git add -N .` してから取り直す（`-N` は内容をステージせず存在だけ登録するので、
ユーザーのステージ状態を壊さない）。

### 2. 一次レビュー（plan を知らない目）

サブエージェントを 1 つ立て、**plan の存在を一切伝えずに**差分だけを見せる。

これが要。「この plan の実装をレビューして」と頼むと、微妙な実装でも
「plan に則っているので問題なし」で流れてしまう。plan は実装の正当化に使えてしまうので、
まず正当化材料を持たない目に通す。

サブエージェントへの指示に含めるもの:

- 差分の取り方（`git diff HEAD` など、範囲を明示）
- 「plan / 設計文書 / `ai-out/` 配下は読まないこと。差分と既存コードだけで判断する」
- 見てほしい軸: 壊れる可能性のある挙動変更、境界・null・エラー処理の抜け、
  既存呼び出し元との不整合、テストの欠落、名前と実体のズレ、意図が読み取れない変更
- 出力: 指摘ごとに `severity` / `title` / `location`（`パス (新L109〜) [h010]`）/ `detail` / `suggestion`
- 「問題がないなら無いと言ってよい。件数を埋めるための指摘はしない」

### 3. 二次レビュー（plan 照合）

一次の結果が出たら、別のサブエージェントに **plan + 差分 + 一次の指摘一覧** を渡す。

やることは 2 つ:

1. **plan との突き合わせ** — plan にあるのに実装されていないもの、plan にない余計な変更、
   plan の意図と食い違う実装を探す。これは plan を読まないと出せない指摘なので、そのまま採用する。
2. **一次の指摘の再評価** — plan を読んだ上で、各指摘を `kept` か `demoted` に分ける。

`demoted` にするのは「plan を読めば意図が分かる」場合だが、**指摘自体は消さない**。
`verdict_note` に「plan のどこを読んでそう判断したか」を書いて残す。
plan 上は意図的でも実装として改善余地があることは普通にあるし、
消してしまうと 2 段階に分けた意味がなくなる。事実誤認だった指摘だけは落としてよい。

plan が無い場合はこの段を飛ばし、一次の結果をそのまま使う。

### 4. グループ分けと解説を書く

ここは自分でやる。サブエージェントは差分を評価するが、
全体を「意図の集合」として再構成するには両方の結果と全体像が要る。

**グループの単位は意図で、ファイルではない。**
rename とそれに追随した import 修正は、何ファイルにまたがっても 1 グループ。
逆に 1 ファイルの中に別々の意図が入っていれば、hunk 単位で別グループに割る。

判断に迷ったら「このグループだけを取り消したら、意味のある単位で機能が戻るか」を考える。
戻るなら 1 グループ、戻らないなら分けすぎ。

**並び順はリスク順**（`build_report.py` が `risk` で並べ替える）。
リスクは「壊れたときの影響 × 壊れやすさ」。共通基盤・認証・データ整合性・
既存の呼び出し元が多い箇所は上。文言修正・フォーマット・テストの追加は下。
読み手の集中力は最初の 10 分に集中しているので、そこに危ない所を置く。

**解説は「diff から読み取れないこと」だけ書く。**
`intent` に書くのは *なぜ* であって *何を* ではない。
「関数を追加した」は diff が語っている。「なぜここに集約したのか、何を安全にしたかったのか」を書く。

意図が読み取れないグループがあったら、そこで止まらず `needs_improvement: true` を立てて
「意図が読み取れない」と findings に書く。無理に物語を捏造すると、
レポートを読んだ人が誤った安心をしてしまう。これが一番まずい。

`hunk_notes` は目を留めてほしい hunk にだけ付ける。全部に付けると誰も読まない。

### 5. レポートを生成して開く

`review.json` を `$W/review.json` に書く。フィールドの詳細は
`references/review-json-schema.md` を読むこと（初回は必ず読む）。

```bash
python "$SKILL/scripts/build_report.py" --hunks "$W/hunks.json" --review "$W/review.json" -o "$W/report.html"
xdg-open "$W/report.html"   # 開けない環境ならパスをそのまま伝える
```

`build_report.py` は hunk id の誤りと**割り当て漏れ**で落ちる。
漏れで落ちたら、それは本当に見落としているということ。`--allow-unassigned` で押し切る前に、
「機械的な追随変更」のようなグループを作って回収できないか考える。

生成できたらユーザーに伝えること:

- レポートのパス（クリックできるように絶対パスで）
- グループ数・指摘数と、上位にどのグループを置いたか
- 「グループごとに『確認して承認』、指摘ごとに採用/却下/保留を付けて、
  最後に 05 でフィードバックを生成 → コピーして、元の作業セッションに貼ってください」

### 6. フィードバックを受け取る

ユーザーが貼ってくるのは、採用された指摘 + 人間のコメントが 1 つになった markdown。
これはそのまま実装の作業指示として扱える。

ただし冒頭に「忖度なしで妥当か精査してください」と入っている通り、
**全部を鵜呑みにして直さない**。LLM の指摘が的外れなこともある。
妥当でないと思うものは直す前にそう言う。それが精査を頼まれた側の仕事。

## 補足

- レポートの入力内容は localStorage に自動保存される。再読み込みしても消えない。
- 同じ差分に再度レポートを出す場合は、`title` を変えると別の保存領域になる。
  同じ承認状態を引き継ぎたいなら `title` と `base` を揃える。
- 差分が数 hunk しかないなら、このスキルは過剰。普通に読んで報告する方が速い。
