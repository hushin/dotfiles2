# plan ファイルの書き方

plan は「実装者に渡す指示書」であると同時に、**将来 `git log` で読まれる唯一の設計説明**になる。
plan ファイル自体は commit 時に本文をコミットメッセージへ移して削除されるので、
ここに書き落としたことは後から取り戻せない。

このスキルの範囲は plan を書き上げるところまで。実装はしない。

## 置き場所

作業リポジトリの `ai-out/plans/<slug>.md`。

`<slug>` は内容が分かる英小文字ケバブケース（`fix-aria-snapshot-drift`,
`url-host-migration` など）。日付や連番は付けない。plan は短命で、同時に何本も走らない。

`ai-out/` は git 管理外である必要がある:

```bash
git check-ignore -q ai-out || echo "ai-out/" >> .git/info/exclude
```

`.gitignore` ではなく `.git/info/exclude` に足すのは、自分の作業ディレクトリの都合を
共有リポジトリに混ぜないため。プロジェクトとして ignore したいと言われたら `.gitignore` へ移す。

## 書く前に調べる

plan の価値は、実装者が同じ調査をやり直さずに済むことにある。先に読むもの:

- 変更対象まわりの既存実装と、そこが今の形になっている理由
- 命名・ディレクトリ構成の慣習（新しい流儀を持ち込まないため）
- テストの置き場所と書き方
- typecheck / lint / test の実際のコマンド（`package.json` の scripts、Makefile、CI 設定）

調べずに書いた plan は、実装段階で必ず崩れる。崩れた前提のまま実装が進むのが一番高くつく。

## 構成

```markdown
# <タイトル。issue があれば `Issue #15: …`>

## Context
なぜこの作業が必要か。現状どうなっていて、何が問題か。
実装者が知らない前提（どのファイルが何を担っているか、なぜ今の形なのか）をここに集める。

## 対応方針
採る方針と、その理由。検討して**見送った案があれば、見送った理由ごと**書く。
これを書いておかないと、実装者やレビュアーが同じ案を再提案してくる。

### 1. <手順>
具体的に触るファイルと変更内容。必要なら差分イメージや表で。

### 2. <手順>
…

## 確認方法
どのコマンドが通れば完了か。typecheck / lint / test / 手動確認の手順を具体的に。

## 対象外
今回やらないこと。スコープが広がるのを防ぐ。
```

見出しは `#` を 1 つだけ、その下は `##` と `###` に収める。
コミットメッセージ本文になったときに階層が破綻しないため。

## 何を書き、何を書かないか

**書く**のは、diff を見ても分からないこと。

- なぜこの方針なのか
- 何を検討して、なぜ見送ったか
- どの制約に縛られているか（互換性、移行期間、外部仕様）
- 実装者が知らない既存コードの事情

**書かない**のは、diff が語ること。「この関数を追加する」は差分を見れば分かる。
手順に具体的なファイル名と変更内容は要るが、コードを全部先に書く必要はない。
判断が済んでいれば、実装は機械的に進む。

逆に、実装中に設計判断が必要になるようなら plan が足りていない。
手順を書きながら「ここは実装者に任せるか」と思ったら、そこを自分で決める。

## 書き終えたら

パスと要点をユーザーに伝えて**止まる**。

- plan のパス
- 対応方針の要約（3行程度）
- 判断に迷って選んだ点、見送った案があればそれ

ここで方針の食い違いが見つかれば、実装を丸ごと捨てずに済む。
**承認を得ずに実装へ進まない。** 実装を続けて頼まれている場合でも、一度ここで区切る。
